## 2. หลักฐานที่วัดได้ (code-grep ทั้ง 5 แพ็กเกจ)

| ตัวชี้วัด | ค่าที่วัดได้ (นับใหม่ด้วย regex ที่ถูก) | อ่านว่าอะไร |
|---|---|---|
| `rounded-[10px]` | **241** | = `rounded-md` เป๊ะ (`--radius: 0.75rem` = 12px, md = 12−2) |
| `rounded-[12px]` | **14** | = `rounded-lg` เป๊ะ |
| `rounded-[8px]` | **7** | = `rounded-sm` เป๊ะ |
| radius arbitrary ทั้งหมด | **270** | อีก 8 ค่า (2/4/6/9/14px) ไม่มี token ตรง — คงไว้ |
| `text-[11px]` | **295** | Tailwind ไม่มี 11px ⇒ ทุกคนเลี่ยงไปใช้ arbitrary |
| `text-[12px]` / `text-[14px]` | 5 / 1 | = `text-xs` / `text-sm` เป๊ะ |
| `text-[8px]` | 2 | เล็กเกิน — **เลื่อนไป Phase D** (แก้ในรอบนี้จะเปลี่ยนพิกเซล) |
| `#10B981` ในคลาส | **302** (text 156 · bg 78 · border 37 · ring 26 · via 5) | สีแบรนด์ hardcode แทน token |
| `<button>` ดิบ vs `<Button>` | **204 vs 326** | 38% ของปุ่มไม่ผ่าน design system |
| `animate-` | **196** | แอนิเมชันเยอะ — ขัดกับ "เรียบง่าย" |
| `backdrop-blur` | 29 | พอรับได้ |
| gradient | 10 | น้อย ไม่ใช่ปัญหา |
| shadow | sm 46 / md 21 / lg 11 | **ดีอยู่แล้ว** ไม่ต้องแก้ |
| ไฟล์ tsx ใหญ่สุด | `Center.tsx` 2,384 · `ShopProductDetail.tsx` 1,841 · `ProductFormDialog.tsx` 1,323 · `ShopCheckout.tsx` 1,238 | จอที่แน่นที่สุด = ที่ต้องลดความหนาแน่น |

**ข้อสรุปสำคัญ:** ปัญหาไม่ใช่ "หน้าตาไม่ทันสมัย" — ปัญหาคือ **ระบบมีอยู่แล้วแต่โค้ดไม่ทำตาม**
ตัวเลข 270 ค่า radius + 301 ขนาดตัวอักษร + 302 สี ที่เขียนเป็นค่าดิบ คือสาเหตุที่หน้าจอแต่ละจอ
รู้สึก "ไม่เป็นชุดเดียวกัน" ทั้งที่ใช้สีชุดเดียวกัน

> **บันทึกความโปร่งใส:** ฉบับแรกของแผนรายงานผิดว่า 884 radius / 233 สี เพราะ regex ในลูปแรก
> ถูกตีความเป็น character class (`[10px]` = ตัวอักษร 1,0,p,x) ตัวเลขข้างบนวัดใหม่ด้วย
> `rounded(-[a-z]+)*-\[[0-9]+px\]` และแยกตาม property แล้ว ทิศทางของข้อสรุปเดิมไม่เปลี่ยน
> แต่ขนาดของงานเล็กลงกว่าที่เคยบอก ~3 เท่า

## 3. บั๊กในเอกสารเอง (ต้นเหตุของ arbitrary values)

`VELNOX_DESIGN_THEME.md` §8 ระบุว่า:

| เอกสารบอก | Tailwind จริง |
|---|---|
| `text-xs` = 11px | **12px** |
| `text-sm` = 12px | **14px** |
| `text-base` = 14px | **16px** |

ตารางนี้ผิดไปหนึ่งขั้นทั้งหมด ⇒ คนเขียนโค้ดที่อยากได้ 11px ตามเอกสารจึงต้องใช้ `text-[11px]`
(295 ครั้ง) นี่คือรากของความไม่สม่ำเสมอ **ต้องแก้เอกสารก่อนแก้โค้ด** ไม่งั้นจะวนกลับมาอีก

## 4. เป้าหมาย 3 ข้อ (วัดผลได้)

1. **ลดจำนวน "ค่าดิบ" ลง ≥ 90%** — จาก ~1,412 จุด เหลือ < 140
2. **ทุกปุ่มผ่าน `Button`** — `<button>` ดิบเหลือ 0 ใน 4 แอป (ยกเว้นที่มีเหตุผลจริง)
3. **1 หน้าจอ = 1 ระดับความหนาแน่น** — ลด element ที่ไม่จำเป็นในจอใหญ่ 4 จอ

### C2 — ข้อเท็จจริง: มี 3 สูตร ไม่ใช่ 2

ตอนเสนอ ผมบอกว่ามี 2 แบบ (pill / tab) แต่พอมองปุ่มทั้ง 40 ตัวจริงพบ **3 สูตร**:

| recipe | ลักษณะ | ที่ใช้ | สถานะ |
|---|---|---|---|
| `tray` | chip เล็กในรางสีเทา, active = การ์ดขาว + เงา | `Income*.tsx` 5 ไฟล์ | **แปลงแล้ว** (ตรงกันทุกไบต์) |
| `dark` | พื้นเข้ม, active = slate-900 | `SellerOrders.tsx:133` (rounded-full) · `SellerProfile.tsx:190` (rounded-lg + text-sm + hover ต่าง) | ยังไม่แปลง — **2 ตัวนี้ไม่เหมือนกันด้วยซ้ำ** |
| `brand` | emerald ทึบ + ไอคอน + จำนวน | `MyShop.tsx:499` และอื่น ๆ | ยังไม่แปลง |

`dark` มี 2 สูตรย่อย (radius ต่าง + hover ต่าง) ⇒ ถ้าแปลงทั้งคู่ตอนนี้จะต้องเดาว่าอันไหนคือ
"มาตรฐาน" ซึ่งเป็นการเปลี่ยนดีไซน์ disguised เป็น refactor **จึงแปลงเฉพาะ `tray` ที่ตรงกันจริง 5 ไฟล์**
และบันทึกอีก 2 recipe ไว้ในคอมเมนต์ของ primitive เพื่อไม่ให้ใครไปคิดสูตรที่ 4 ขึ้นมาใหม่
| C3 | ปุ่ม action ที่เหลือ (สแกนแล้วมีน้อย) | `velshop`, `velcenter` | นับจริงก่อน-หลัง |
| C4 | ตรวจว่า dialog/sheet ที่ประกาศเอง 5 ไฟล์ใช้ primitive กลางได้ไหม | 5 ไฟล์ที่ grep เจอ | ไม่มี `createPortal` ที่เขียนเองใหม่ |

### ข้อค้นพบ: ตัวเลข "204 ปุ่มดิบ" ทำให้เข้าใจผิด

พอแยกประเภทจริง (2026-11-10):

| ประเภท | จำนวน | ควรใช้ `<Button>` ไหม |
|---|---|---|
| segmented / toggle (className เป็น template literal + ternary) | **40** | **ไม่** — ต้องมี primitive ของตัวเอง |
| มี `aria-pressed` (filter chip) | **10** | **ไม่** |
| list row / disclosure / upload wrapper / floating pill | ~145 | **ไม่** — เป็น widget ไม่ใช่ปุ่ม |
| action button จริง (bg-slate-900 / bg-brand) | **5** | ใช่ (และบางตัวเป็น floating pill) |

**สรุป:** การบังคับ 204 ปุ่มให้เป็น `<Button>` จะทำให้ UI **แย่ลง** เพราะ `Button` มี base class
(`h-11 px-4 py-2 rounded-md text-sm font-medium`) ที่จะไปทับ layout ของ filter chip, list row
และ overlay

**ปัญหาจริงไม่ใช่ "ไม่ได้ใช้ Button" — แต่คือ "เขียน pattern เดียวกันซ้ำ 40 ที่"**
(period picker ใน 5 ไฟล์ Income*, status filter ใน SellerOrders/MyShop, segment tab ใน SellerProfile)
นั่นคือสิ่งที่ C2 ควรแก้ และได้ผลทั้งความสม่ำเสมอและลดโค้ด

**ความเสี่ยง:** ปานกลาง — primitive ใหม่ต้องรองรับทั้ง pill (rounded-full) และ tab (rounded-md)
จึงควรมี 2 variant ไม่ใช่ 1

## 9. PHASE E — ลด motion

`animate-` 196 จุด. หลักการ: **แอนิเมชันต้องบอกเหตุ (เปิด/ปิด/กำลังโหลด) ไม่ใช่ตกแต่ง**
- เก็บ: `animate-spin` (loading), `animate-in/out` ของ dialog/sheet
- ลด: animation ที่วิ่งตลอดเวลา (เช่น pulse บน element ที่ไม่ได้สื่อสถานะ)
- เคารพ `prefers-reduced-motion`

**ตรวจรับ:** grep แยกประเภทได้ว่าเหลือ animation อะไรบ้าง + owner ดู

## 12. ทางเลือกที่ควรถามก่อนเริ่ม

**รูปแบบความเรียบง่ายที่คุณต้องการคือแบบไหน?**

1. **เท่าเดิมแต่เป็นระบบ** — เก็บหน้าตาวันนี้ไว้ แค่ทำให้สม่ำเสมอ (Phase A+B อย่างเดียว) เร็ว ปลอดภัย ไม่ต้องตัดสินใจอะไร
2. **เรียบขึ้นจริง** — ลดของในการ์ด ลดจำนวนสี/ขอบ ลดข้อมูลซ้ำในจอใหญ่ (A+B+C บางส่วน+D)
3. **ทันสมัยขึ้น** — เพิ่มพื้นที่ว่าง ใช้ตัวอักษรใหญ่ขึ้น 1 ขั้น ลดเส้นขอบ ใช้ elevation แทน border (ต้องดูของจริงทุกจอก่อนอนุมัติ)

ผมแนะนำ **2** เป็นค่าเริ่มต้น: ได้ผลที่รู้สึกได้จริง โดยไม่เสี่ยงกับ flow ที่เพิ่งซ่อม
